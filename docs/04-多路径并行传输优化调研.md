## 一、现有「无线+有线」并行机制剖析（v0.1.0 实现回顾）

### 1.1 机制总结

| 环节 | 实现 | 代码 |
|---|---|---|
| 有线链路 | USB AOA 双角色：Host 侧 controlTransfer 52/53 请求对端进 accessory 模式，双端 `openAccessory` 拿 ParcelFileDescriptor，Java 流读写 | `UsbAccessoryLink.kt` |
| 启用条件 | 三条件齐备：本端 `usbEnabled` 设置 + 对端 `Cap.USB` 能力位 + 链路 attached；`fileReady` 帧带 `usb:1`，接收端完成期望 = streams+1 | `FileTransferEngine.sendFiles` |
| 并行调度 | `ChunkScheduler` 单原子游标多消费者（隐性 work-stealing：快链路循环快自然多拿块） | `FileTransferEngine.kt:972` |
| 聚合 | 数据块帧自带 `(fileIdx, chunkIdx)`，接收端位图乱序去重，任何链路送达即计入 | `handleSinkStream` / `ReceiverState.writeChunk` |
| 完成判定 | BYE 计数闭环（正常 BYE/流断开都算一次）+ 10min 兜底 + 30s 无进展保险 | `awaitCompletion` |
| 半双工争用规避 | USB 纯写 sink（hello 无应答，AEAD 校验即认证），读端由常驻接收循环独占，双端同时互发安全 | `sendUsbSink` |

设计要点正确且是业界空白：**调研未发现任何公开项目做「局域网点对点 + WiFi 多流 + USB 有线条带化 + 位图乱序聚合」**
（GitHub 检索仅学生仿真项目；LocalSend 92.5k 星仍是单流 HTTPS；Speedify 需云端汇聚服务器）。

### 1.2 发现的缺陷（按严重度排序）

| # | 缺陷 | 后果 | 位置 |
|---|---|---|---|
| D1 | **丢块无重传**：AEAD 校验失败仅丢弃该块；sink 中途死亡时已被游标分配的块永久丢失 | USB 拔线/WiFi 抖动 → 尾部缺块 → 全文件 SHA-256 失败 → 整个传输失败。这是并行链路最大的健壮性短板 | `writeChunk`（丢弃）+ 无补发协议 |
| D2 | **无每链路信用/权重**：快慢链路按抢锁 race 分块，慢链路可囤积大量在飞块（4MB/块） | 尾部拖延（慢链路最后几块拖长总时长）；stall 链路囤块即 D1 | `ChunkScheduler.next()` |
| D3 | **位图每块全量重写**：每收一块，读整个 `.bm` 文件→改一位→整文件写回 | O(chunks²) 小 IO；大文件 2500+ 块时可见的元数据开销 | `updateBitmap` |
| D4 | **发送端全量暂存**：SAF URI 先整文件拷进 cache（顺带 SHA-256），再按块读第二遍 | 发 10GB 文件多占 10GB cache + 双倍读 I/O；cache 满即失败 | `stage()` |
| D5 | **接收端双写**：先写 `.part`，完成后整文件再拷进 MediaStore | 接收侧多一倍写 I/O（60MB/s 链路下盘速度可能成为瓶颈） | `publishFinal` |
| D6 | Host 侧 AOA 用 fd 流（每次 write 一 URB，16KB 上限） | 未见 UsbRequest 异步多队列的流水线增益（仅 Host 侧可改） | `UsbAccessoryLink` |
| D7 | USB 块大小与 TCP 相同（默认 4MB 一帧 flush） | USB 链路突发大帧 + 16KB 分包，HOL 与尾部粒度粗 | `sendUsbSink` |
| D8 | `WIFI_MODE_FULL_HIGH_PERF` 已被官方废弃并自动映射为 LOW_LATENCY（后者 javadoc 明言 *Throughput may be reduced*）【官】 | 新版 ROM 上传输锁语义悄然改变 | `WifiLocks.holdTransfer` |

D1/D2 属协议层缺陷，D3-D7 属实现效率，D8 属兼容性。

## 二、调研结论：无 root / Shizuku 前提下的可行路线矩阵

### 2.1 传输层多路径技术

| 路线 | 结论 | 依据（等级） |
|---|---|---|
| **MPTCP（内核）** | ❌ **死路，勿投入**。三重闸门：① GKI defconfig 全系无 `CONFIG_MPTCP`（android13~16 mainline 核验 0 处）【官】；② 加 subflow 的 netlink PM 命令全部要求 CAP_NET_ADMIN，shell uid 无此 capability【官】；③ shell 下 `ip route`/`ip` 配置一律 Permission denied（`fs_config.cpp` 全系统仅 3 个二进制带 file cap）【官+社实测】 | kernel.org mptcp 文档、netlink specs mptcp_pm.yaml、GKI defconfig、shizzi 兼容性实测 |
| **MP-QUIC** | ⚠️ 技术存在但不建议整体引入。`draft-ietf-quic-multipath` v21（2026-03）仍是草案；唯一生产级实现是阿里 **xquic**（C，Android NDK 可用，已在大规模 App 验证），quic-go PR 被关闭、msquic 未发布【社】。对我们：借鉴其**按路径信用窗口 + 每路径独立 CC** 设计即可，不必引入整库（LAN 场景 QUIC 用户态加密+系统调用开销反而可能负收益，与 01 调研结论一致） | github.com/alibaba/xquic、quicwg/multipath |
| **应用层条带化（现状）** | ✅ **就是 Android 上唯一可行的多路径路线**，业界无现成轮子，方向正确 | 综合检索 |
| **FEC（RS/RaptorQ）** | ❌ 默认不值得：收益条件是高 RTT×高丢包×低时延（直播/卫星）；LAN RTT 1-5ms、丢包 <1% 时选择性 ARQ 代价 ≈ 丢包率本身，FEC 固定多付 10-30% 带宽【官/学：SRT、RFC 6330、kcptun】。✅ 值得抄的是 mqvpn 的 **reinjection（尾块跨链路冗余复制）**：仅对超时未确认块在另一链路复制一份，可开关 | SRT 文档、github.com/mp0rta/mqvpn |
| **BLE/蓝牙数据面** | ❌ 维持 01 调研结论：EDR 1-2Mbps，增益 <0.5%，只配发现/控制 | 01 调研 |
| **STA+热点/P2P 双 WiFi** | ❌ 单射频分时，无真实增益；WiFi7 MLO 对 App 不可控（无控制 API，仅 MloLink 信息类）【官】 | WifiManager reference |
| **WiFi Aware(NAN)/P2P R2** | ➖ Android 16 P2P2（USD 发现/PCC 兼容组网）是**发现层**升级而非吞吐升级，数据面仍普通 P2P 速率；碎片化，只做能力探测 | WifiP2pManager reference |

### 2.2 有线路线（本次最大增量发现）

| 路线 | 结论 | 依据（等级） |
|---|---|---|
| **AOA 现状** | USB2 HS bulk 理论 53.24MB/s、实测 35-42MB/s，已接近满载；AOA 协议文档只按 FS/HS 描述【官】。**冷知识：`f_accessory.c` 自 android11-5.4 起就带完整 SuperSpeed 描述符（wMaxPacketSize=1024, bMaxBurst=6，注释明写 support super speed）【官】——即内核从未把 AOA 钉死在 USB2，只是从无公开实测。双 USB3 旗舰 + 全功能 C-C 线 + `svc usb getUsbSpeed` 读实际协商速率即可验证【测】。注意 fd 读写每次 syscall 仅 16KB（TX 4 深度流水、RX 单请求），SS 下瓶颈会转为 syscall 开销 | developer.android.com usb/accessory、kernel common f_accessory.c |
| **AOA Host 侧优化** | ✅ Host 内核不绑定 accessory 接口驱动，App 可 `claimInterface + UsbRequest` 异步队列（多请求并发 16KB）替代同步流写，吞吐与 CPU 双优【官：UsbRequest.MAX_USBFS_BUFFER_SIZE=16384】。gadget 侧仍只有 fd（无解） | UsbRequest/UsbDeviceConnection 源码 |
| **NCM/RNDIS gadget（`svc usb setFunctions ncm`）** | ✅✅ **本次调研最重要发现：shell uid（Shizuku adb 模式）即可执行**。证据链：`svc usb` → `IUsbManager.setCurrentFunctions` 要求 `MANAGE_USB`，而 **com.android.shell 的 manifest 持有 MANAGE_USB + TETHER_PRIVILEGED + CHANGE_NETWORK_STATE**【官】。且 gadget 被对端枚举成功后，Tethering 模块收 `USB_STATE` 广播**自动**对 usb0 启动 DHCP 服务端+NAT——无需用户开任何开关【官：Tethering.java handleUsbAction】。NCM 需 gadget HAL 1.2+（Android 11+ 机型），rndis 无此门槛但**钉死 USB2**【官】 | frameworks/base packages/Shell/AndroidManifest.xml、UsbCommand.java、packages/modules/Connectivity Tethering.java |
| **手机对手机 usb0 网络** | ⚠️ 条件可行：host 侧 GKI 内核内置 `CDC_NCM/RNDIS_HOST` 驱动自动出 usb0【官】；**framework 自动跟踪的分水岭是 Android 15**：`EthernetTracker` 的接口正则从 `eth\d+` 放宽为 `(usb|eth)\d+`（V 起）【官】——即 Android 15+ host 手机插上即得 ETHERNET transport 网络 + 自动 DHCP 客户端；Android 13/14 host 端默认不认 usb0（厂商 overlay 可放宽），这正是社区 phone-to-phone tethering 两极分化的根源【社实测吻合】。13/14 兜底：无法用 shell 配 IP（无 CAP_NET_ADMIN），只能引导用户系统设置 | EthernetTracker.java、android.stackexchange #103505 |
| **NCM over USB3** | ⚠️ 内核两侧（f_ncm bMaxBurst=15 / cdc_ncm host）与 HAL（可上报 super speed）全链路 SS 就绪【官】；**phone-to-phone SS 实测数据缺失**【测】。若真机协商上 5Gbps，有线链路理论可达数百 MB/s，远超 AOA 的 40MB/s —— 这是把「有线并行」从 +40% 变成 +300% 的唯一途径 | f_ncm.c、gki_defconfig、UsbGadget HAL 1.2 |
| **经 Shizuku 直调 startTethering** | ✅ 备选通道：shell 持 TETHER_PRIVILEGED，可经 ShizukuBinderWrapper/UserService 反射调 `TetheringManager.startTethering(TETHERING_USB)`（shizzi/testtap-egress 两项目实证）【社】。与 `svc usb setFunctions` 二选一或互为兜底（后者绕开 entitlement 检查更稳） | shizzi、android-testtap-egress |
| **MTP host 模式** | ➖ 可行但不优：`android.mtp.MtpDevice`（公开 API）+ `getPartialObject64` 分段拉，手机当 host 拉对端「文件传输」模式；同步 bulk 请求-应答模式，预期 20-35MB/s，低于 AOA 纯 bulk【官+社】。仅作未来「拉取对方相册」场景备用 | developer.android.com reference/android/mtp/MtpDevice |

### 2.3 Shizuku 边界速查（shell uid 能/不能）

- ✅ 能：`svc usb setFunctions/getUsbSpeed/resetUsbGadget`；经 binder 以 shell 身份调 startTethering；`settings put global/secure`；运行 APK nativeLibraryDir 自带静态二进制（`lib*.so` + extractNativeLibs）或落 `/data/local/tmp` 执行；dumpsys 全家（链路体检）。
- ❌ 不能：`ip link/addr/route`、iptables（无 CAP_NET_ADMIN）；`cmd wifi force-hi-perf-mode/force-low-latency-mode`（**root-only**，WifiShellCommand 源码硬检查）；`EthernetManager.enableInterface/updateConfiguration`（缺 NETWORK_STACK 系权限）；普通 App 直调 startTethering（TETHER_PRIVILEGED 为 signature|privileged）。
- ⚠️ FGS：dataSync 6h/24h 配额 Android 15 起严格执行，超时 onTimeout 不 stopSelf 会崩；建议传输服务补 `connectedDevice`（USB 外设交互恰符合）或 `specialUse` 类型声明。

## 三、优化建议

### P0 · 修协议健壮性（不动架构，收益最大）

1. **块级补发协议（修复 D1）**：接收端 `awaitCompletion` 收满 BYE 后不直接进校验，先扫内存位图得缺失块清单，经控制会话发 `fileRepair{token, missing:[(f,c)…]}`；发送端收到后对缺失块重开一轮 sink（任意链路，优先快链路），循环直至位图全满或空转两轮才校验。改动集中在 `handleOffer` 尾部 + 发送端 `sendFiles` 第 6 步，v1 接收端对旧版对端天然兼容（旧版不会发 repair 帧）。
   - 这同时把「USB 拔线」「sink 半途死」「AEAD 偶发坏块」从致命错误降级为一次补发轮。
2. **每链路在飞字节上限（缓解 D2）**：`sendStream/sendUsbSink` 取块前检查本链路 inflight（已取未 ACK 字节）≤ 上限（USB 初始 8-16MB、TCP 每流 2 块），BLEST 思想——慢链路少囤块，尾部不被拖死。真正按权重调度放 v2。

### P1 · 有线链路升级（速度天花板跃迁）

3. **新增 usb0/NCM 链路类型（对 `svc usb setFunctions ncm` 路线）**：
   - 新 `UsbNetLink`：Shizuku 就绪时执行 `svc usb setFunctions ncm`（失败依次降级 `rndis`、AOA）；对端枚举到 ETHERNET transport 后，`ConnectivityManager` 注册 `NetworkRequest(TRANSPORT_ETHERNET)` → `Network.bindSocket` 把 N 条 TCP 数据流绑定到 usb0 网络（与 WiFi 流完全并存，帧格式不变，接收端零改动）。
   - host 侧识别：`LinkProbe` 的接口过滤增加 `usb\d+`；对 Android 13/14 host（框架不跟踪 usb0）给用户引导（系统设置→网络→以太网）或回退 AOA。
   - 连接后 `svc usb getUsbSpeed` 记录实际协商速率，SuperSpeed 机型把 USB 流数提到 2-4 条。
   - 能力位：`Cap.USB_NET = 16`，与 `Cap.USB` 并存协商。
4. **AOA Host 侧改 UsbRequest 异步队列（D6）**：Host 端 `claimInterface` + 深度 8-16 × 16KB 的 UsbRequest 队列替代 FileOutputStream；gadget 侧维持 fd。双端互发时两端角色对称（各自 host 侧优化）。
5. **AOA over SuperSpeed 一次实验（低成本高价值）**：双 USB3 旗舰 + 全功能线，AOA 握手后读 `getUsbSpeed`。内核描述符已就绪，若协商上 SS，即使 fd 路径受 16KB/syscall 限制也应显著超 42MB/s【测】。

### P2 · 传输路径效率（盘与 CPU）

6. **位图内存化（D3）**：位图常驻内存（10GB/4MB 块 = 2.5KB，可忽略），落盘改为每 2s 或每 64 块一次 + BYE 时强制；断点续传读盘仅在恢复时一次。
7. **发送端零暂存（D4）**：`ContentResolver.openAssetFileDescriptor` 拿 seekable pfd → `RandomAccessFile(pfd.fileDescriptor)` 直读分块（绝大多数本地 SAF 源可 seek；不可 seek 再走现有暂存）。token 改用 `(name,size,mtime)` 确定性派生，SHA-256 改为发送时单遍增量（每块读出后 update 摘要，发完即得），省一半读 I/O 与全部暂存写。
8. **接收端直写 MediaStore（D5）**：API 29+ 用 `openFileDescriptor(uri,"rw")` 对 pending 行直写（`raf.seek(chunkIdx*chunkSize)`），校验通过后仅 `IS_PENDING=0`，删除 `.part` 拷贝环节；失败再回退现路径。
9. **WifiLock 修正（D8）**：传输锁显式改 `WIFI_MODE_FULL_LOW_LATENCY`（反正是同一映射）并停止依赖 HIGH_PERF 常量；文档记录「低延迟模式可能压吞吐」的官方提示，留设置项让真机数据说话。

### 顺带 · 无线侧可做的小项

- 自建热点指定频段：`startLocalOnlyHotspot(SoftApConfiguration)`（API 33+）`setBands(BAND_5GHZ)` + `setChannels`；**SDK 无法指定信道带宽**（无 setChannelWidth），且 5GHz 可能被监管/OEM 静默回退 2.4GHz——起热点后读回实际信道（36-165 判 5GHz）再向用户展示真值【官】。
- 双机空闲时 2s 微基准（各链路各发 8MB 探测块）自动定初始权重与流数，替代固定 4 流。

## 四、舟协议 v2：MPLB 多路径链路绑定核心（自研方向）

> 命名：Multi-Path Link Bonding。目标：把 v1「块帧可乱序聚合」的隐性约定，升级为显式的
> **链路插件化 + 租约调度 + 接收端信用 + 位图 SACK + 补发闭环** 的多路径传输核心。

### 4.1 分层

```
应用层    offer/accept/inbox/chat（不变）
─────────────────────────────────────────────
调度层    LeaseScheduler（租约）· CreditManager（每链路字节信用）· HealthMonitor（EWMA 速率/RTT/错误率）
─────────────────────────────────────────────
链路插件  WifiTcpLinkPool(N流) · UsbAoaLink(fd) · UsbNetLinkPool(usb0 N流) · [未来: P2P/xquic 实验道]
─────────────────────────────────────────────
数据面    统一块帧 (fileIdx, chunkIdx, len, AEAD)（v1 兼容）+ 链路序号 lane
```

### 4.2 核心机制（相对 v1 的增量）

1. **块租约（Chunk Lease）**：`scheduler.next()` 改为 `lease()`——块出队即挂 `(linkId, deadline=now+T_link)`；HealthMonitor 按 EWMA goodput 动态给 T（USB 30-40MB/s 时 T≈1s/块）。超时未确认块自动回收入队，可被其他链路取走。**从根上消灭 D1/D2**：stall 链路不再囤死块，无需等最终校验才发现缺块。
2. **接收端驱动的每链路信用**：接收端按各链路消费速度发 `linkCredit{lane, bytes}`（QUIC MAX_DATA 思想）；发送端某链路 inflight ≤ credit 才 lease。慢链路信用小（BLEST 防阻塞），快链路信用大——**速率比例分配自动成立，无需显式权重**。
3. **位图 SACK + 补发轮**：控制会话周期性（或每 N 块）上报累积位图；补发不再等收尾，缺失块超阈值即触发针对性重发（P0 的机制化版本）。
4. **尾块冗余复制（可选开关，替代 FEC）**：传输进入最后 ~5% 时，未确认块同时在两条链路各发一份（mqvpn reinjection 思路），用 <5% 冗余换尾部时延，对 USB+WiFi 异速链路收益最明显。
5. **每块 AEAD 不变 + 密钥升级**：fileKey 逐文件不变，但 nonce 加入 `lane`（多链路同块重复发送时 nonce 复用会破坏 GCM 安全性——v2 补发/复制场景必须 nonce 覆盖 lane 或重加密），这是 v1 没暴露仅因从不重发。
6. **零拷贝收发**：发送端 mmap/直读 + 单遍增量哈希；接收端 pending URI 直写 + 位图内存化（P2 条目协议化）。
7. **能力协商 v2**：`Cap.USB_NET`、`Cap.LEASE_SCHED`（新调度）等新位 + `fileReady` 版本字段；旧版对端自动回退 v1 行为（双向兼容是 v1 兼容策略的延续）。

### 4.3 与备选方案的关系

- 不引入 xquic/MP-QUIC 整库：MPLB 在应用层已达同等聚合语义，且保留逐块 AEAD、零拷贝与 USB 非网络链路（AOA 流）的表达能力（QUIC 只能跑在 IP 链路上，AOA fd 链路它覆盖不了——这是自研的硬理由）。
- 不引入 FEC：LAN 场景 SACK+补发+尾块复制已覆盖，系统性 FEC 是负收益。
- MPTCP/内核路径全部封死（见 2.1），自研应用层是 Android 无 root 唯一路线。

### 4.4 落地顺序建议

1. P0 两项（补发 + inflight 上限）可在 v1 代码直接落，一次真机回归验证 USB 拔线场景。
2. UsbNetLink + NCM 路线独立分支验证（需 Shizuku 真机 + Android 15 host 或 13/14 引导流程），实测 SS 协商与 NCM 实际吞吐后决定 USB 侧默认链路类型（AOA 兜底）。
3. 租约+信用调度（MPLB 核心）在以上稳定后替换 ChunkScheduler，对外协议帧保持 v1 兼容演进。

## 五、验证清单（真机）

| 实验 | 方法 | 判定 |
|---|---|---|
| AOA 实际协商速率 | 双 USB3 旗舰 + C-C 全功能线，AOA 握手后 `svc usb getUsbSpeed`（Shizuku） | SS 则有线 >42MB/s 可期 |
| NCM 链路吞吐 | `svc usb setFunctions ncm` + iperf 式微基准（绑定 usb0 Network） | 对比 AOA；SS 机型看能否 >100MB/s |
| Android 15 host 自动配网 | 15+ host 插线即查 `ConnectivityManager` ETHERNET 网络 | 有 usb0 网络 = 免配置成立 |
| 13/14 host 兜底 | 同上（预期失败） | 确认引导/回退 AOA 路径 |
| 双端同时互发（NCM+WiFi） | 反向传输打满时正向吞吐 | 验证 NCM 全双工与 WiFi 并存无干扰 |
| USB 拔线中途 | 传 20GB 文件 30% 时拔线 | v1：失败；P0 后：补发轮完成 |
| 慢链路尾拖 | 人为限速 WiFi（远离 AP）+ USB 并行 | P0-2 后总时长应 ≈ 理论混合最优 |
