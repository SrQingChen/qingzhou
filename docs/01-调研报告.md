# 青舟 调研报告

> 调研日期：2026-09-22 · 作者：SrQingChen
> 结论服务于决策：局域网/热点场景下，安全前提下最快的发现速度与传输吞吐。

---

## 1. 传输速度基线（802.11ax 现实认知）

- 802.11ax/WiFi 6 是链路层能力，App 无法强制开启；能做的是**榨干链路**并在劣化链路时引导用户。
- 实测参考值：
  - 5GHz 热点直连（host↔client 单跳空口）：**50~90 MB/s**
  - 同一路由器下两台手机（空口时间减半）：**40~80 MB/s**
  - 小米旗舰（14/15/17 系列，WiFi7 2x2）热点 AP 模式为 **WiFi6 5GHz AP**（WiFi7 手机开热点也降级，国内无 6GHz 频段）
  - 2.4GHz 热点：仅 2~6 MB/s → 必须引导用户开 5GHz AP
- 瓶颈在协议栈而非空口：LocalSend（每文件单 TCP 流 + TLS）实测仅 17~20 MB/s。

### 突破口（本项目的性能设计依据）

| 手段 | 收益 | 依据 |
|---|---|---|
| 大文件分块（1~4MB）+ 3~6 条 TCP 并行流 | 单流 ~300Mbps → 多流 600~700Mbps，约 2 倍 | iperf 多流实测、ESnet 调优指南 |
| SO_RCVBUF/SO_SNDBUF 调大至 4~8MB | 避免窗口受限 | BDP 计算（LAN RTT 1~5ms） |
| FileChannel.transferTo（sendfile 零拷贝） | CPU 每 GiB 降 ~70% | IBM/NVIDIA 零拷贝分析 |
| 分块 AES-GCM（ARMv8 硬件指令）替代整流 TLS | 加密吞吐 GB/s 级，50~100MB/s 下加密不是瓶颈；且 sendfile 与整流 TLS 不兼容，分块明文读+逐块加密是零拷贝友好的 | ARMv8 crypto extension |
| 传输期 WifiLock WIFI_MODE_FULL_HIGH_PERF | 消除省电策略导致的吞吐波动（影响比一切提权手段都大） | Android 官方文档、XDA 实测 |

### 已排除的技术（有明确理由）

- **BBR**：厂商内核普遍未编入，App 无法启用；且 LAN RTT 1~5ms 场景 cubic 已瞬间打满窗口，BBR 无优势。
- **KCP**：官方自述"为延迟设计非吞吐"，LAN 低丢包环境无优势还多耗 10~20% 带宽。
- **QUIC（ngtcp2/quiche）**：LAN 收益仅 0/1-RTT 建连；大吞吐下用户态加解密+系统调用开销可能慢于内核 TCP。留作后期实验选项。
- **WiFi Aware (NAN) 作主通道**：硬件/固件碎片化严重，热点开启时基本不可用，Apple/Android 互通差。仅保留能力探测（可用则报告，不依赖）。

## 2. 设备发现方案对比

| 方案 | 速度 | 热点场景 | 耗电 | 结论 |
|---|---|---|---|---|
| UDP 广播/多播 announce | <100ms 可控 | host↔client 可用 | 低（传输期才持锁） | **主通道**（必须持 MulticastLock，小米尤其严格） |
| 网关 IP 直连 probe | 零等待 | **热点场景最快路径**（客户端读 LinkProperties 网关 IP 直接 TCP 探测） | 极低 | 热点加速通道 |
| BLE 广播 | 1~5s | 连接前感知对方（互传联盟/Quick Share 同思路） | 最低，息屏可常驻 | 辅助通道（省电偏好下默认关） |
| NSD (mDNS/DNS-SD) | 1~3s 系统调度不可控 | 可用 | 系统托管 | 生态兼容通道（可选） |
| WiFi Direct | 3~10s（GO 协商） | 与热点互斥 | 高（发现期） | 无路由器场景兜底链路（v1 含，做好超时回退） |

关键事实：
- Android 热点自带 DHCP（192.168.x.0/24，Android 11+ 随机化网段），热点主机即网关。
- 双机场景不存在 client 隔离问题（只有 host↔client 一条路径）。
- MulticastLock 存在"失锁"问题（Google issue #247596083），需周期性重取 + 直连 probe 兜底。
- WifiP2pManager 未废弃：Android 16 加入 WiFi Direct R2（USD/PCC）；5GHz P2P 可经 `setGroupOperatingBand()` 请求但依赖芯片；6GHz 不可用于 P2P。P2P 链路默认多落在 2.4GHz 802.11n（100~300Mbps），通常低于热点直连。
- 无现有 WiFi 时可编程自建局域网：`startLocalOnlyHotspot()`（Android 13+ 仅需 NEARBY_WIFI_DEVICES）。

## 3. 多链路聚合可行性（回答作者提问）

**问题：能否同时利用 WiFi（热点）+ 蓝牙 + 有线等链路聚合，超越任何单链路速率？**

| 组合 | 结论 | 原因 |
|---|---|---|
| WiFi + 蓝牙 | **无价值** | BT 经典 EDR 实际 ~1-2Mbps、BLE 数据 ~0.1-0.5Mbps，对比 WiFi 400Mbps+ 增益 <0.5%，徒增耗电与调度复杂度。蓝牙只配做发现/控制通道。 |
| STA + 热点 / STA + P2P 双 WiFi | **无增益** | 同一颗射频芯片分时工作，空口仍是瓶颈（WiFi7 MLO 已在硬件层做这件事，且 App 无控制权）。 |
| USB-C 有线（ECM/NCM 网卡模式） | **理论可行，成功率低** | 一端开 USB 网络共享，另一端 USB host 枚举出 usb0 以太网卡 → 变为普通 IP 链路（USB2.0 实测 ~300-400Mbps），与 WiFi 是真正不同的物理通道。但依赖双方 host 模式 + 内核 CDC 驱动 + gadget 支持，设备差异大。 |
| 多设备并发（1 对多） | **真实增益场景** | 天然利用多条空口/多台发送端。 |

**决策**：v1 不承诺聚合；但架构上把块调度器设计为「块 → 链路 → 流」三级多链路感知，任何新链路（USB、P2P）都是插件式挂载；USB-C 有线链路放 v2+ 实验特性。

## 4. 安全握手

- LocalSend 模式（自签 TLS + 证书 SHA-256 指纹 TOFU + 可选 PIN）被验证可用，但整流 TLS 与 sendfile 零拷贝冲突。
- **本项目方案**：Noise Protocol Framework（XX 用于首次配对、IK 用于复用已配对密钥）：
  - 原语 X25519 + ChaCha20-Poly1305（握手/小消息）+ AES-256-GCM（大文件分块，硬件加速）+ BLAKE2b（校验）
  - 首次配对：双方展示 6 位指纹短码人工核对（SPAKE2 思想的简化：对比指纹哈希），可选二维码
  - 已配对设备：PSK（Noise IK）1-RTT 建立会话，毫秒级
  - 分级：小消息（≤64KB 文本/剪贴板）UDP 单包 AEAD + 抗重放窗口，免握手直发；大文件分块逐块 AEAD + 全文件 BLAKE2b，天然支持并行与断点续传
- 安全红线（Quick Share "QuickShell" 10 漏洞教训）：**绝不零点击自动接受文件**；接收默认需确认（仅对已配对设备开放"自动接收"开关）；对端身份强校验。

## 5. 超级岛（焦点通知）

- 接入方式：原生 Notification extras 注入 `miui.focus.param`（JSON ≤3072 字节）+ `miui.focus.pics`（Icon bundle），无 SDK。
- 协议版本判定：`Settings.System.getInt(resolver, "notification_focus_protocol", 0)` → 1=OS1 / 2=OS2 焦点通知 / 3=OS3 超级岛；OS2/OS3 数据接口相同。
- 传输进度最适模板：`param_island.smallIslandArea.combinePicInfo.progressInfo`（胶囊态环形进度）+ `bigIslandArea`（展开态文件名/速率/剩余时间 timerInfo）；完成时 `cancel:true` 收岛。
- **白名单风险**：OS2/OS3 有 SystemUI 白名单 + 签名校验 + XMSF 云端鉴权三重校验，未申请权限的应用不上岛（降级普通通知）。官方申请：小米开发者平台提报 + 邮件 mipush-permission@xiaomi.com（免费、周期数周、年底续期）。
- **Shizuku 兼容模式**（尘露已验证）：鉴权 fail-open —— 上岛期间经 Shizuku 临时切断 `com.xiaomi.xmsf` 联网（`cmd connectivity set-package-networking-enabled false`），收岛后恢复。工程要点：单线程串行、意图代数防竞态、状态落盘防进程被杀后全机断网遗留。
- MIUI 14 及以下无此接口，自然降级。
- 趋势：Android 16 原生 Live Updates（`Notification.ProgressStyle`）正成为统一标准，OPPO ColorOS 16/vivo 原子岛均已认原生 API → 通知层做四级降级。

## 6. 澎湃 OS 1/2/3 跨版本兼容

| 维度 | 要点 |
|---|---|
| targetSdk | 36（同时覆盖 OS1/2/3；Play 2026-08 起要求 ≥36）；compileSdk 37；minSdk 26 |
| 前台服务 | A14+ 强制 foregroundServiceType；OS2 起 dataSync 型 FGS 累计 6h 上限（onTimeout 自愈）；传输用 dataSync |
| 通知权限 | POST_NOTIFICATIONS 运行时；小米"后台弹通知"默认拒（FGS 通知一般不受限） |
| Powerkeeper | 锁屏后台联网受限 → 传输期 FGS + 引导页（省电无限制/关 WLAN 助理/锁后台） |
| WiFi 权限 | targetSdk 33+ P2P/NSD/扫描需 NEARBY_WIFI_DEVICES 运行时权限（neverForLocation 免定位）；A13 以下需 ACCESS_FINE_LOCATION |
| 受限网络 | 无 internet 的热点可能被判"受限"，Socket 需 bindSocket 到 WIFI transport Network |
| 16KB page size | Android 15+ 新机要求，原生库需对齐（影响 libsodium 引入方式） |

## 7. Shizuku 提权加速边界

可行（shell uid）：`dumpsys wifi`（读频段/协商速率/省电状态，做传输前链路体检）、`settings put global wifi_scan_always_enabled 1`、`ip route`/`ss -i` 诊断、xmsf 网络开关（超级岛兼容模式）。
不可行（需 root）：`iw dev wlan0 set power_save off`（nl80211 需 CAP_NET_ADMIN）、BBR sysctl。核心吞吐优化（WifiLock/多流/缓冲）全部无需提权。
